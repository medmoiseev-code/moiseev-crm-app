# AGENTS.md — Axio CRM

Этот файл содержит стабильные правила работы с проектом. Спорные продуктовые решения и временные договорённости сюда не добавляются.

## 1. Цель проекта

- Axio CRM — демонстрационное браузерное CRM-приложение для показа рабочих сценариев клиники.
- Публичная версия предназначена только для демонстрации и проверки интерфейса.
- В репозитории и демоверсии разрешены только вымышленные пациенты, несуществующие контакты и тестовые медицинские сведения.
- Демоданные сохраняются локально в браузере и не синхронизируются между устройствами.

## 2. Основные принципы

- Не добавлять реальные персональные, медицинские или контактные данные.
- Не добавлять в репозиторий пароли, токены, API-ключи, резервные копии, экспорты и файлы импорта.
- Не удалять и не преобразовывать пользовательские данные без явного требования задачи.
- Не менять функциональность за пределами поставленной задачи.
- Не придумывать продуктовую или бизнес-логику при отсутствии утверждённого правила.
- Если необходимое решение не определено, остановиться и запросить уточнение.
- Сохранять обратную совместимость демоданных и данных браузера, если задача явно не требует иного.

## 3. Правила разработки

- Проект использует JavaScript, Vite и стандартные команды из `package.json`.
- Перед изменениями изучить связанные компоненты, обработчики, стили, тесты и модель сохраняемых данных.
- Делать минимальные локальные изменения; не проводить сопутствующий рефакторинг без запроса.
- Не менять архитектуру проекта без отдельного явного задания.
- Не дублировать существующие функции, константы и интерфейсные компоненты.
- Сохранять существующие публичные имена, форматы данных и связи между сущностями, если их изменение не входит в задачу.
- Учитывать старые записи в `localStorage`; изменение структуры данных требует безопасной совместимости или согласованной миграции.
- Не редактировать сгенерированный каталог `dist` вручную.
- Не добавлять зависимости без явной необходимости и согласования.
- Не подавлять ошибки пустыми обработчиками и не скрывать ошибки сборки или тестов.
- Не изменять чужие незакоммиченные изменения и несвязанные файлы.

## 4. Правила интерфейса

- Сохранять единый визуальный язык существующего интерфейса: компоненты, размеры, отступы, цвета и состояния.
- Новый элемент должен использовать существующий компонент или визуальный паттерн, если подходящий уже есть.
- Не менять масштаб всего приложения ради исправления отдельного элемента.
- Не оставлять пустые области после удаления интерфейсных элементов; аккуратно перераспределять место в пределах изменяемого блока.
- Кликабельность должна быть понятна по курсору, hover- и focus-состояниям.
- Обычные действия выполняются одинарным кликом; двойной клик не использовать без отдельного требования.
- Клик по одному интерактивному элементу не должен запускать действие родительской строки или соседнего элемента.
- Диалоги и формы не должны закрываться из-за перемещения указателя или выделения текста за их границами.
- Сохранять доступ к основным действиям при переключении вкладок и состояний экрана.
- Проверять интерфейс при длинном тексте, пустых значениях и на узком экране.

## 5. Правила бизнес-логики

- Данные пациента не удаляются только потому, что их отображение убрано из таблицы или другого представления.
- История должна отражать фактически совершённые значимые действия и сохранять их порядок.
- Повторное нажатие сохранения не должно создавать дубли или повторно применять одно действие.
- Обновление страницы не должно повреждать или неожиданно сбрасывать сохранённые демоданные.
- Сброс демоданных восстанавливает исходный демонстрационный набор; пользовательские настройки интерфейса сохраняются.
- Резервное копирование и восстановление не должны молча принимать повреждённую или несовместимую структуру данных.
- Удалённое или пустое примечание не должно оставлять связанный с ним визуальный индикатор.
- Изменение одного рабочего сценария не должно незаметно менять фильтры, поиск, сортировки, историю и соседние сценарии.
- Архитектура процессов, набор этапов, виды задач и модель лечения не определяются этим документом.

## 6. Правила самопроверки

- Перед сдачей просмотреть итоговый diff и убедиться, что в нём нет посторонних изменений и чувствительных данных.
- Выполнить `npm run test` для изменений, затрагивающих бизнес-логику или покрытые тестами сценарии.
- Выполнить `npm run build` после каждого изменения проекта.
- Исправить ошибки тестов и сборки, вызванные текущей задачей.
- Проверить основной изменённый сценарий вручную, включая отмену, повторное действие и обновление страницы.
- Проверить связанные интерактивные элементы, чтобы изменение не перехватывало их клики.
- В итоговом сообщении перечислить изменённые файлы, результат проверок и известные ограничения.
- Не заявлять, что проверка выполнена, если соответствующая команда или сценарий не запускались.

## 7. Правила работы с Git

- Перед началом и перед сдачей проверять `git status`.
- Считать существующие незакоммиченные изменения пользовательскими и не перезаписывать их.
- Не использовать `git reset --hard`, принудительный checkout и другие разрушающие команды без прямого разрешения.
- Не включать в коммит несвязанные изменения, `node_modules`, `dist`, локальные настройки, секреты и выгрузки данных.
- Коммит должен описывать одну законченную задачу понятным сообщением.
- Не выполнять commit, push, merge, rebase, публикацию или переписывание истории без явного запроса.
- Перед публикацией убедиться, что в текущей и публикуемой истории отсутствуют реальные данные и секреты.
- Помнить, что удаление файла из текущей версии не удаляет его из предыдущих коммитов.
